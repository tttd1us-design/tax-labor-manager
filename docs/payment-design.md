# 세금 노무 매니저 — 결제 모듈 설계안 (2주차)

## 1. 배경 및 제약

- **스파크 결정 (S-1013-f3009f)**: "유료 PG 결제 연동 및 외부 API 키 발급 등 비용 또는 계약 수반 사항은 오픈 베타 테스트 완료 후 대표이사 최종 결재를 득할 것."
- **결재 전 진행 불가**: 결제 모듈은 설계 단계에 먨물며, 실제 PG사 API 키 발급, 계약서 서명, 결제 코드 구현은 대표이사 최종 결재 후에만 진행한다.
- **목표**: MVP의 무료 프로토타입(index.html)에 프리미엄 기능 제공을 위한 결제 플로우를 설계한다.

## 3. 결제 모듈 아키텍처 (설계만)

### 3-1. 클라이언트-서버 분리 구조

```
┌─────────────────────────────┐
│  tax-labor-manager (정적)    │
│  index.html (Vanilla JS)     │
└──────────┬──────────────────┘
           │
           │ (무료 배포: GitHub Pages)
           │
┌──────────▼──────────────────┐      ┌────────────────────────┐
│  결제 프록시 서버 (Node.js)    │◄──►│  PG사 API (Toss/KCP/KG)  │
│  - 결제 금액 검증            │      │  - 승인/취소/환불       │
│  - 웹훅 검증 (서명)          │      └────────────────────────┘
│  - 구독 상태 관리            │
│  - 결제 내역 기록            │
└──────────┬──────────────────┘
           │
┌──────────▼──────────────────┐
│  구독 DB (PostgreSQL 등)     │
│  - user_id, 결제 금액, 등급   │
│  - 결제 일시, 만료 일시      │
│  - 재결제 일시              │
└─────────────────────────────┘
```

### 3-2. 결제 플로우

1. **프리뷰 → 결제 버튼 클릭**
   - 사용자가 프리미엄 기능 버튼 클릭
   - 클라이언트에서 결제 프록시 서버로 `POST /api/create-payment` 요청 (금액, 등급, 사용자 식별자 전달)

2. **서버-side 검증**
   - 결제 금액 검증 (클라이언트가 요청한 금액이 아닌, 서버가 정의한 금액만 charged)
   - 결제 금액 변조 방지: 클라이언트가 금액을 전송하지 않는다. 서버가 등급→금액 매핑 테이블에서 조회.

3. **PG사 결제창 호출**
   - 서버가 PG사 결제 생성 API 호출 → 결제 검증 토큰(imp_uid 또는 paymentKey) 발급
   - 토큰을 클라이언트에 반환
   - 클라이언트가 PG사 JavaScript SDK 또는 리다이렉트 방식으로 결제 실행

4. **결제 완료 후 웹훅**
   - PG사 → 결제 프록시 서버 웹훅 전송
   - 웹훅 서명 검증 (PG사 제공한 시크릿 키로 HMAC 검증)
   - 검증 통과 시 → DB에 구독 기록 저장 (결제일시, 만료일시 = 결제일 + 30일)

5. **클라이언트에게 구독 상태 전달**
   - 결제 완료 후 클라이언트가 `GET /api/subscription-status?user=xxx` 호출
   - 서버가 DB 조회 → 구독 등급 및 만료 일시 반환

### 3-3. 보안 설계

| 항목 | 설계 내용 |
|------|-----------|
| **금액 검증** | 클라이언트 절대 금액 전송 불가. 서버가 등급→금액 매핑으로 검증. |
| **웹훅 서명 검증** | PG사 웹훅에 서명 포함 여부 확인. 서명 불일치 시 거부. |
| **사용자 식별** | 세션 방식 미사용. 브라우저 localStorage에 anonymous ID 생성 (UUID v4). ID는 암호화 저장. |
| **결제 정보 암호화** | 카드번호 등 민감 정보는 PG사가 직접 처리. 앱 서버는 결제 검증 토큰만 다룸. |
| **CORS** | 결제 프록시는 지정 도메인(예정: tax-labor-manager.github.io)만 허용. |
| **HTTPS 의무** | 결제 프록시 서버는 반드시 HTTPS. (Vercel/Render Free 등 TLS 지원 플랫폼 사용) |

### 3-4. 예상 비용 (결재 필요 항목)

| 항목 | 월 예상 비용 | 비고 |
|------|-------------|------|
| 결제 프록시 호스팅 (Vercel Free tier) | 0원 | Free tier로 충분 (Serverless Function + PostgreSQL) |
| 데이터베이스 (Supabase Free tier) | 0원 | 500MB, 월 100만 행 |
| **PG사 계좌개설 수수료** | **미확인** (결재 대상) | Toss: 0원 / KCP: 500만 원 / KG: 200만 원 |
| **거래 수수료** | **미확인** (결재 대상) | Toss: 2.75% / 카드사 추가 수수료 별도. 연동 수수료 0.5~1% 별도. |
| **법인등록증사본·사업자등록증** | 0원 | 대표본인 소지 |

## 4. 클라이언트-프록시 통신 API 설계

### 4-1. `POST /api/create-payment`
```json
Request:
{
  "tier": "Pro",        // "Free" | "Pro" | "Business"
  "user_id": "uuid-v4"   // 브라우저 localStorage에서 생성한 익명 ID
}

Response:
{
  "payment_id": "pay_xxx",
  "amount": 9900,
  "order_name": "Tax Labor Manager Pro 1개월 구독"
}
```

### 4-2. `GET /api/subscription-status?user_id={uuid}`
```json
Response:
{
  "tier": "Pro",
  "expires_at": "2026-11-15T23:59:59.999Z",
  "is_active": true
}
```

### 4-3. `POST /api/webhook` (PG사 → 서버)
```json
{
  "payment_key": "xxx",
  "order_id": "xxx",
  "status": "DONE",
  "amount": 9900,
  "signed_by_pg": true
}
```

## 5. 결제 모듈 통합 지점 (클라이언트)

정적 `index.html`에 다음을 추가할 예정 (결재 후 구현):

2. **구독 상태 표시**
   - `localStorage`에 `tlm_subscription` 키로 등급/만료일 캐싱
   - 만료 7일 전 알림 배너 표시

3. **결제 완료 콜백 처리**
   - 결제 성공 리다이렉트 URL에 `?payment=success` 파라미터
   - 페이지 로드 시 구독 상태 재조회 후 UI 언락

## 6. 향후 확장 가능 영역

- **구독 갱신 자동화**: 만료일 3일 전 자동 결제 시도 (사용자 재동의 필수)
- **정기결제 (구독) vs 1회결제**: 초기에는 1회 결제 방식으로 시작하여, 피드백 후 정기결제 전환 검토
- **화폐 단위 다국어 지원**: 향후 해외 진출 시 USD/EUR 지원
- **쿠폰/프로모션 코드**: 베타 테스터에 한해 30일 무료 체험 쿠폰 발급
